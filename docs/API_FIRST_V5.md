# API 우선 공시 추출 설계 v5

## 발송 명세

사용자가 제시한 63개 보고서의 항목명과 순서를 발송 명세로 사용한다. 기존 presentation.CONTRACTS의 구조화 44종, 재무 3종, RAW_PROFILES의 원문 16종을 유지한다. 기업명은 굵게, 접수번호는 메시지에서 숨기고 원문 링크에만 사용한다.

## 취득 흐름

1. 공시 유형을 공식 API에 연결한다. API가 없는 유형은 사유 no_structured_api를 기록한다.
2. API 조회 결과를 같은 접수번호와 정확히 대조한다. 다른 보고서의 데이터는 붙이지 않는다.
3. 정상 응답 중 발송 명세에 해당하는 항목을 선택한다. 참석 여부 같은 부수 항목만 반환된 것을 추출 성공으로 간주하지 않는다.
4. 데이터 없음이나 접수번호 불일치라면 조회일을 31일 전까지 확장하여 최초접수일 차이를 확인한다. 키·권한·요청한도 오류에는 기간 확장을 반복하지 않는다.
5. API 핵심 항목을 확보하면 API로 발송한다. 핵심 항목이 일부 부족하면 해당 접수번호 원문에서 부족한 항목만 보완한다.
6. API 값은 원문으로 덮어쓰지 않는다. 원문에서 같은 항목에 서로 다른 값이 발견되거나 여러 증권 레코드와 원문 행의 대응이 불명확하면 보완을 보류한다.
7. 원문 조회가 실패해도 확보한 API 값은 유지한다. 둘 다 확보하지 못하면 실패 표시와 원문 링크를 유지한다.

재무정보는 연결/별도·통화·기간을 보존하며 원문 숫자를 기간 정보 없이 합치지 않는다. 부수 주식 종류나 자금용도 세부 항목이 적용되지 않는 경우를 일괄 실패로 처리하지 않는다.

## 출처와 진단

각 결과에 source, field_sources, evidence, checked_at을 둔다. evidence에는 endpoint, status, 날짜/재무기준, exact_receipt_rows, field_count, reason, original_reason, original_error를 저장한다. 원시 예외 메시지나 API 인증키는 저장하지 않는다.

source 구분:
- OpenDART 구조화 정보
- OpenDART 구조화 정보 + 원문 표 보완
- 원문 표
- 추출 불가 · 원문 확인

API 시도와 최종 원문 사용을 구분한다. API를 호출했지만 013을 받은 사례를 API 데이터 사용 성공으로 표시하지 않는다. 실패 결과도 진단은 보존하되 추출 성공 캐시에는 저장하지 않는다. 캐시 버전 v5로 이전 결과를 재사용하지 않는다.

GitHub runtime-reports 브랜치의 발송 이력에 API 진단과 항목별 출처를 포함한다. 예전 이력의 출처는 과거 체크포인트와 현재 캐시의 증거 수준을 구분하여 표시한다.

## 실제 검증과 한계

NICE평가정보 및 LS에코에너지의 2026-10-26 타법인 주식 취득 공시는 서버 재조회에서 당일과 10월 전체 기간 모두 013을 반환했다. 이는 당시 역사적 응답을 복원한 결과가 아니라 재조회 결과다.

사용자가 제시한 애경케미칼 회사합병결정 공시는 cmpMgDecsn에 연결된다. 실제 API 응답을 별도 읽기 전용 진단 대상으로 추가했다. 알림은 재발송하지 않는다.

합성 검증은 44개 API 성공 경로, API 보존·원문 보완, 원문 실패, 접수번호 불일치, 기간 확장, 원문 충돌, 다중 증권 보완 금지, 기존 63종 출력 및 표 변형 검증을 포함한다. 코드 검사 통과와 서버 실응답 검증을 같은 의미로 보고하지 않는다.
